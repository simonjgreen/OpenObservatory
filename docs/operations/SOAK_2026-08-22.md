# 72-hour acceptance soak, 2026-08-22 to 2026-08-25 — **PASSED on continuity**

The fourth attempt at the acceptance soak, and the first to complete a valid
72-hour restart-free window.

**Nobody staged this run.** It began as the reboot that followed the mains power
cut which killed attempt three, at `2026-08-22T05:50:47Z`, and was recognised as
a soak candidate 41 hours later rather than started as one. That is worth stating
plainly: the run was not set up, instrumented in advance, or protected. It was
noticed. Everything below is measured off a window that happened to be clean, not
one that was arranged to be.

## Every gap in the window

Two, both confirmed as lost audio, enumerated from the journal rather than
inferred from the counters:

| when (UTC) | duration | reason | at frame | frames lost |
|---|---|---|---|---|
| 2026-08-23 23:16:19.277 | 0.0404 s | `frame_deficit` | 57,262,310,400 | 15,501 |
| 2026-08-24 20:35:00.299 | 0.5566 s | `overrun` (`alsa_overrun=True`) | 86,721,523,200 | 213,744 |

The second is the one with a mechanism worth naming. It landed during peak bat
activity, alongside multi-megabyte clip writes. **Corrected 2026-08-29:** the
mechanism named here — and in the comment at
`src/open_observatory/station.py:339` — is the pre-[[ADR-030 - ALSA ring and capture thread|ADR-030]] one, clip writes
taking a slot in a thread pool shared with the ALSA read. Since [[ADR-030 - ALSA ring and capture thread|ADR-030]] the
read has its own single-thread executor and holds no slot in that pool, so it
cannot lose one. What survives is [[ADR-033 - Retention is paced|ADR-033]]'s point: an executor partitions
queueing, not the GIL, so the writes can still delay the loop that issues the
read past the 500 ms ring. That is why evidence writing has its own isolated executor. The isolation
held well enough that this cost 0.56 s across 72 hours rather than the "11 gaps
and 8 overruns in five minutes" the same mechanism produced before it existed.

Nothing else in the window lost audio. No gap arrived in the ~300 s pairs that
were the retention sweep's signature ([[ADR-061 - Operator keep flag|ADR-061]]).

## What ran during the window, and what it did not cause

The inside-observer display was updated over the air to firmware 0.2.5 between
`2026-08-24T11:43:45Z` and roughly `11:45Z` — a 1.1 MB image published to the
station and served over HTTP, inside the soak window.

**It caused neither gap.** The first preceded it by 11.5 hours and the second
followed it by 8.8 hours. This is recorded because the load was added
deliberately by an agent working on the station mid-soak, and "we added load and
the run still passed" is only worth anything if somebody checked the timing
rather than assuming it.

`evidence.dropped` reached ~1,138 across the window (588 `activity-v1`, 426
`ultrasonic-pass-v1`, 124 `birdnet-v2.4`). **This is not a fault and must not be
read as one.** The evidence queue is capped at 32 deliberately, sized below what
the 120 s native ring can cover, so a refusal is counted at the door instead of
becoming a silent extraction miss the counter cannot show. Capture always wins.
Against 87,723 acoustic events in the same window it is a rounding error — but
those particular detections exist without clips, which is a fact about the
record, not a defect in it.

## Storage

Disk closed at **0.8107** against an 0.85 watermark, having *fallen* from 0.8174
the previous day. `retention_sweep_keeping_up` true throughout, zero consecutive
barren sweeps, zero rows claiming missing files. The mid-run climb was the
overnight native-clip bulge and it receded, which is the behaviour [[ADR-062 - Retention walks live assets|ADR-062]] was
written to produce and the first soak in which it has been observed working
across a full 72 hours.

## What this run does and does not settle

**Settles:** the capture-continuity criterion, on a valid window, with margin.

**Does not settle:** every other box in [[ACCEPTANCE_CRITERIA]]. None of them
was formally exercised during this window. Unplug/replug was not tested, the
sweep/alias tests were not run against this stream, and nothing here touches the
API, MQTT, MCP or UI criteria. This run closes one box. It is not an acceptance
pass, and the word "complete" remains unavailable.

It also cannot settle a mechanism with a period longer than the window. 72 hours
covers the daily class that the 12-hour run of 2026-08-14 explicitly could not.

## Lessons from previous attempts, checked against this one

[[SOAK_2026-08-14]] closes by listing three things that were not checkable
during that run and that any future attempt must check. All three were checked
here:

- `unclean_restart` — true for the window, but referring to the *previous* run's
  ending, not this stream's. The health note is worded so that this reads as an
  alarm on every check until the next clean shutdown; it is not one here.
- `clock_reanchors` — **0**, and `clock_last_step_s` 0.0.
- `retention_sweep_keeping_up` — true throughout, disk trend flat then falling.

**The [[ADR-063 - Clock re-anchor|ADR-063]] anchor check — done, and it passes.** [[ADR-063 - Clock re-anchor|ADR-063]]'s defect was that
capture anchored its frame-to-UTC mapping 1 m 45 s *before* NTP first
synchronised after a boot, making 49 hours of timestamps 106 seconds early while
continuity remained perfect and correct throughout. This stream also started
immediately after a power-cut reboot, which is the same setup, and
`clock_reanchors: 0` does **not** rule the defect out — [[ADR-063 - Clock re-anchor|ADR-063]]'s failure
produced no re-anchor either, because the wrong anchor was simply never
revisited. So the two times were compared directly:

| event | time (UTC) |
|---|---|
| `systemd-timesyncd` initial clock synchronisation | **2026-08-22T05:50:15.922813Z** |
| capture stream `started_utc` (the frame-to-UTC anchor) | **2026-08-22T05:50:47.084278Z** |
| anchor relative to sync | **+31.16 s — after** |

The anchor was taken half a minute *after* the clock was correct, so [[ADR-063 - Clock re-anchor|ADR-063]]'s
defect did not recur and the UTC timestamps written across this window are
sound. (The journal renders in BST and `fake-hwclock` opens the boot in late
July, exactly as [[ADR-063 - Clock re-anchor|ADR-063]] describes; both were accounted for in reading this.)

Continuity would have been unaffected either way: it is a monotonic-clock
property, as [[ADR-063 - Clock re-anchor|ADR-063]] records.
